## 2. 三条产品路线(样式差异的根源)

竞品的 UI 差异不是审美问题,而是**路线**问题。理解路线才能决定抄谁。

### 路线 A — 桌面重型(Acrobat / Foxit / PDFelement)
- **样式**:顶部 Ribbon 或菜单栏 + 左侧导航面板(缩略图/书签/附件/签名) + 右侧属性面板 + 底部状态栏
- **特征**:功能密度极高,学习曲线陡。Foxit 刻意模仿 Office Ribbon 以降低迁移成本
- **服务对象**:法务、合规、企业 IT(需要 SSO、组策略部署、审计日志)
- **对本项目**:❌ **不该抄**。你的用户是无账号的轻量用户,不需要企业能力

### 路线 B — 网页轻量(Smallpdf / Sejda / Lumin / Canva)
- **样式**:首屏一个大拖拽区 → 进入编辑器 → 顶部工具栏 + 中间画布 → 右上角 Apply/Download
- **特征**:**按任务而非按工具组织**。Smallpdf 是「21 个工具卡片」的入口页,Sejda 是「Upload → 操作 → Apply changes → Download」的线性流程
- **服务对象**:偶发用户,不想装软件
- **对本项目**:✅ **最该参考**。你的定位和它们最接近

### 路线 C — 设计工具化(Canva)
- **样式**:左侧模板/素材面板 + 中间画布 + 右侧属性 + 顶部工具栏;强调拖拽、素材库、品牌套件
- **特征**:把 PDF 当「设计稿」而非「文档」。导入后**拆解成可编辑元素**
- **对本项目**:⚠️ **部分参考**。你的布局已经是 Canva 式,但 Canva 的「素材库/品牌套件」需要云端,不适合你

## 3. 值得参考的 — 按优先级

### 🟢 P0 — 低成本、高感知、与你定位一致

#### R1. 把已有的 redact 做成显式「涂黑 / 密文」工具 ⭐ 最推荐
**行业情况**:Adobe 称其为 "legal-grade redaction",2026 年 AI 自动脱敏是最大热点。**关键认知**:评测明确指出「AI 标记 ≠ 脱敏」——画个黑矩形不是脱敏,原文还在内容流里,几秒就能提取出来。真脱敏必须从内容流删除。

**你的情况**:你已经**有真脱敏引擎**了 —— `core/writer/redact.ts` + `core/mupdf/mupdfEngine.ts` 用 MuPDF 的 `Redact + applyRedactions` 做字节级删字,PDFium 也能删对象。但它**只被文本编辑内部调用**,用户看不到这个能力。

**建议**:新增一个「涂黑」工具。拖矩形 → 走 MuPDF redact → 真删除。这是竞品要收费的核心能力,你已经有 80% 的代码。

**工作量**:小(引擎已有,缺 UI 与 overlay 类型)
**为什么优先**:这是唯一一个「你已经实现了但用户用不到」的高价值功能。

#### R2. 表单字段创建
**行业情况**:Acrobat / Foxit / PDFelement / Sejda 都支持。Sejda 明确列出可创建 Text / Multiline / Dropdown / Checkbox / Radio。PDF Expert 在这项被评测列为「弱」。

**你的情况**:README 明确写「不支持从空白 PDF 创建新 AcroForm 字段(需要 MuPDF 写入完整 AcroForm 字典)」—— 这个判断**过于保守**。我在生成本次验证素材 S4 时,用 **pdf-lib 的 `doc.getForm().createTextField/createCheckBox/createRadioGroup/createDropdown` 成功生成了四类字段**,并通过 pdf-lib 重新读取验证字段名与类型全部正确。

**建议**:用 pdf-lib 的 form API 实现字段创建。不需要动 MuPDF。

**工作量**:中(pdf-lib API 已存在,需要 UI + overlay 类型)
**价值**:从「只能填表」升级到「能做表」,是 F11 的完整化。

#### R3. 顶部工具栏按任务分组(PDF Expert 的 Tab 模式)
**行业情况**:PDF Expert 顶部是 `Edit / Annotate / Scan & OCR` 三个 tab,评测称「工具很多但不觉得被淹没」。Foxit 用 Ribbon 分组,Smallpdf 用工具卡片分组。

**你的情况**:`Toolbar.tsx` 平铺 **9 个纯图标按钮**(`↖ ✎ ☐ ◑ ☰ T ▦ ✏ ✒`),仅靠 `title` 提示。这正是我在验证计划 **A8** 记录的问题:`✎`(编辑文字)/ `T`(文字)/ `↖`(选择)三者视觉相近,新用户无法区分。

**建议**:改为 3–4 个分组 Tab:
- **编辑** — 选择 / 编辑文字 / 表单
- **注释** — 高亮 / 便签 / 画笔 / 签名
- **插入** — 文字 / 图片
- **页面** — 页面管理

或至少保留平铺但**加可见文字标签**(图标 + 4 字以内的字)。

**工作量**:小(纯 UI 重组)
**价值**:一次解决 A8 + B9(工具语义重叠)

#### R4. 首屏拖拽上传
**行业情况**:Canva / Sejda / Smallpdf / Lumin **全部**支持拖拽,且是首屏主交互。

**你的情况**:`EmptyState.tsx` 是 3 个按钮(模板 / 打开 / 新建空白),**没有拖拽区**。

**建议**:给 EmptyState 加全屏拖拽区,并支持拖拽到已有文档上替换。

**工作量**:小
**价值**:网页工具的第一印象动作,缺失显得不专业。

#### R5. 适应宽度 / 适应页面
**行业情况**:所有阅读器标配。
**你的情况**:验证计划 **B5** 已记录缺失。你只有 7 个固定缩放档位。
**建议**:加 `fitWidth` / `fitPage` 两个模式。注意:我在优化计划里已把 `stepZoom` 改成能正确处理非档位值(如 fitWidth 算出的 1.17),正是为这个预留的。
**工作量**:小
**价值**:阅读 PDF 最常用的两种缩放。

#### R6. PDF 内搜索 (Ctrl+F)
**行业情况**:所有编辑器都有(Canva 和 Smallpdf 反而没有,是它们的短板)。
**你的情况**:验证计划 **B6** 已记录缺失。你的 `pdfjs` 已加载了文本层,`getTextContent()` 现成可用。
**建议**:Ctrl+F → 搜索框 → 高亮命中 → 上一个/下一个。
**工作量**:中
**价值**:20 页以上文档的刚需。

### 🟡 P1 — 值得做,但要评估成本

#### R7. OCR(扫描件文字识别)
**行业情况**:Acrobat / Foxit / PDFelement(23 语言)/ PDF Expert / Sejda 都有。评测把它列为「是否需要」的判定标准之一:只要处理过纸质扫描件就需要。2026 年 AI OCR 在低质量扫描、手写、非拉丁文字上准确率大幅提升。

**你的情况**:完全缺失。你的 S5 扫描件 fixture 目前只能走「无文字层」的降级路径。

**评估**:
- **优点**:补齐最大功能缺口,能把扫描件变成可编辑文档
- **代价**:Tesseract.js 约 2–4 MB WASM + 语言包(中文包另加数 MB);识别慢(主线程会卡,需 Worker);准确率不如云端 AI OCR
- **与定位冲突?**:不冲突 —— Tesseract.js 是纯本地运行的,契合「不上传」

**建议**:做,但**按需懒加载**(和 MuPDF 一样的策略),默认不加载。中文语言包单独按需拉取。

#### R8. 裁剪 (Crop)
**行业情况**:全部具备。PDF Expert 评测特别提到裁剪对扫描件很实用。
**你的情况**:缺。
**建议**:`PageMeta` 加 `cropBox` 字段,导出时应用。中等工作量。
**价值**:扫描件场景刚需。

#### R9. 页码 / 水印 / 页眉页脚
**行业情况**:全部具备,且都是「一键批量」型功能。
**你的情况**:缺。
**建议**:pdf-lib 直接 `drawText` 逐页画,可复用你现有的 `flatten` 管线。工作量小。
**价值**:批量文档的常见需求,实现成本低。

#### R10. 打字生成签名(手写体)
**行业情况**:Sejda 提供 10+ 种手写体,输入名字自动生成签名。Acrobat / PDFelement / PDF Expert 也都有「打字 / 手绘 / 上传图片」三种方式。
**你的情况**:`SignatureDialog.tsx` 只有**手绘**一种。
**建议**:补「打字」和「上传图片」两种。打字需要手写体字体(可用开源手写体,或复用你已有的 CJK 字体方案)。
**工作量**:小–中
**价值**:很多人签不出好看的签名,打字生成是实际使用率最高的方式。

#### R11. 压缩体积
**行业情况**:Smallpdf 的招牌功能(评测称能把 50 MB 压到 5 MB 以内)。PDFelement 支持批量压缩。
**你的情况**:缺。而且**反向问题**:你此前的导出会因整字体嵌入膨胀到 7 MB+(已在优化 O1 修复为子集嵌入,现在约 70 KB)。
**建议**:O1 之后导出体积问题已大幅缓解,压缩的紧迫性下降。可选做:图片降采样 + 重复资源去重。
**优先级调整**:O1 修复后从 P1 降到 P2。

#### R12. 超链接编辑
**行业情况**:Sejda / Acrobat / Foxit / PDFelement 支持。
**你的情况**:缺。
**建议**:pdf-lib 可创建 Link 注解。中等工作量,感知度一般。

#### R13. 护眼 / sepia 阅读主题
**行业情况**:PDF Expert 有 day / night / **sepia** 三种阅读主题,评测特别提及。Acrobat 也有。
**你的情况**:有暗色 + 5 种主题色,但**没有 sepia**。
**建议**:加一个 sepia(米黄底 + 深棕字)阅读主题。
**工作量**:很小(CSS 变量即可)
**价值**:长文阅读场景很实用,成本极低。

#### R14. 双页 / 分栏阅读
**行业情况**:PDF Expert 与 Acrobat 支持单页/双页/连续三种布局。
**你的情况**:只有连续滚动单页。
**建议**:加「双页并排」模式。中等工作量。
**价值**:书籍、杂志类文档需要。

### 🔴 P2 — 不建议抄(与定位冲突)

| 能力 | 为什么不做 |
|------|-----------|
| **云端 AI 摘要 / 对话问答** | 必须上传文档到服务器,直接违背你「文件不离开设备」的核心卖点。**替代方案**:若要做,只做 BYO-key(用户自带 API key,浏览器直连)或纯本地小模型,且必须默认关闭 |

## 4. 你的独有优势(应该主动强调的)

### 4.1 「网页版就完全离线」是真正的差异化

| 产品 | 文件是否上传服务器 | 离线可用? |
|------|:---:|:---:|
| Smallpdf | ✅ 上传(处理后 1 小时删除) | ❌ |
| Canva | ✅ 上传 | ❌ |
| Lumin | ✅ 上传(云端原生) | ❌ |
| Sejda 在线版 | ✅ 上传 | ❌ |
| Sejda **桌面版** | ❌ 本地 | ✅ 但要**安装** |
| Acrobat / Foxit / PDFelement | ❌ 本地 | ✅ 但要**安装** |
| **本项目** | ❌ **本地** | ✅ **打开浏览器就行** |

评测里反复出现一个担忧:「在线 PDF 编辑器对敏感文档安全吗?」答案是「涉及合同、财务、HIPAA/NDA 的文档应该用桌面版」。**你恰好给出了第三种答案 —— 不用安装,也不上传。**

这是**唯一一个竞品都无法同时满足的组合**。建议:
- 首屏、README、空状态都明确写「文件不上传、不联网、无需登录」
- 做一个**可验证**的证明:断网后仍能完整工作(可加一个「离线自检」提示)
- 考虑加 Service Worker + PWA,让「离线可用」变成真正的产品能力(README 路线图已提到 PWA)

### 4.2 字节级 redact

竞品把「真脱敏」当付费核心能力卖,而你已经实现了(只是没暴露)。见 R1。

### 4.3 商业模式的天然优势

竞品定价:

| 产品 | 价格 |
|------|------|
| Acrobat Pro | $19.99/月 |
| Foxit PDF Editor | $10.99–16.99/月 |
| Smallpdf Pro | $12/月 |
| PDFelement | $79.99/年 或 **$129.99 永久** |
| PDF Expert | $79.99/年 或 **$139.99 永久** |

**观察**:PDFelement 和 PDF Expert 都把「**永久授权**」当作核心差异点 —— 因为用户厌倦订阅。而你的项目**没有服务器成本**(纯前端、无后端),天然适合「买断制」或「开源 + 付费版」,不需要像 Smallpdf 那样靠订阅覆盖算力。这是结构性的成本优势,值得在定位上利用。

## 5. 建议的落地顺序

| 顺序 | 项目 | 类型 | 状态 | 理由 |
|------|------|------|:---:|------|

| 2 | **R3 工具栏按任务分组** | 样式 | ✅ **已落地**(后经一次收敛,见下) | 一次解决 A8 + B9;纯 UI 重组,风险低 |
| 3 | **R4 首屏拖拽 + R13 sepia 主题** | 样式 | 待办 | 两个都是小工作量、高感知 |
| 4 | **R5 适应宽度/页面 + R6 PDF 搜索** | 功能 | 待办 | 补齐阅读器基线能力 |
| 5 | ~~**R2 表单字段创建**~~ | 功能 | ❌ **已取消** | 见下方「R2 取消说明」 |
| 6 | **R9 页码/水印 + R10 打字签名** | 功能 | 待办 | 成本低,覆盖面广 |
| 7 | **R7 OCR** | 功能 | 待办 | 缺口最大但成本也最高,单独排期 |
| 8 | **R8 裁剪 / R14 双页** | 功能 | 待办 | 按用户反馈决定 |

**建议先做 1–3**:前 3 项都是「低成本、高感知」,能快速拉近与竞品的观感差距,且不引入新的技术风险。

### R2 取消说明(表单字段创建)

本节写于"R2 值得抄"的判断之上,该判断**已被推翻**。后续按「按任务收敛」原则重做功能面时,表单功能被**整体移除**,不只是不再往前做:

- 已实现的只是「读原 AcroForm 字段 + 导出时用 pdf-lib 重建」,**无法新建字段树**,也丢失原 PDF 的 JavaScript / formatting / 自定义外观。这属于半成品 —— 用户拿到的"能填的表单"和真实表单体验差距很大。
- 因此删除了 `FormFieldItem`、`parseFormFields`(三个引擎的接口 + 实现)、`features/forms/`、`core/writer/formFields.ts`、`FormFieldOverlay`、`F` 快捷键,以及 README 中"可以创建新字段"的说明(该说明本身与实现不符,详见验证计划 B11 一类的文档漂移问题)。
- 同时移除的还有**便签**(与「文字」叠加层重叠)和**「编辑文字」独立工具**(与「选择」语义重叠 —— 正是 A8/B9 记录的问题;改为「选择」下双击文本块进入编辑)。

**教训**:竞品分析里的"值得抄"是**功能面**的判断,不是**可行性**的判断。R2 的能力上限(pdf-lib 能建字段)被当成了"只差 UI",但真正缺的是字段树、脚本与外观一致性 —— 那是另一个量级的工作。

### R3 后续收敛

R3 当初把 9 个工具压成 3 组 9 个按钮,仍保留了「编辑文字」与「表单」。后续进一步收敛为 **7 个工具 / 3 组**:

| 组 | 工具 |
|---|---|
| 编辑 | 选择 |
| 注释 | 高亮 / 涂黑 / 画笔 / 签名 |
| 插入 | 文字 / 图片 |

TopBar 上的「打开项目」按钮也已删除(与「打开 PDF」并列时极易混淆),「全文格式化」从常驻开关改为**打开 PDF 时的确认弹窗**。

## 5.1 R1 落地记录(涂黑 / 密文)

R1 已实施完成。要点与实测数据如下,供后续参考。

**关键发现:复用文本编辑的 redaction 参数会产出「假脱敏」。**

文本编辑路径调用的是 `applyRedactions(false, 0, 0, 0)` —— 只删字,图片与矢量原样保留。这是**有意为之**(改文字不该顺手删掉旁边的图),但直接拿它做涂黑工具就危险了。`scripts/experiment-redact.mjs` 用对照组量化了差异:

| 参数组 | 被覆盖文字 | 图片(被覆盖半边) | 图片(未覆盖半边) | 矢量图元 |
|---|---|---|---|---|
| 基线(未涂黑) | 存在 | 1400 px 红 | 1400 px 蓝 | 381 px |
| `(false, 0, 0, 0)` 仅删字 | 已删除 | **1400 → 1400 存活** | 1400 → 1400 | **381 → 381 存活** |
| `(false, 2, 2, 0)` 全量 | 已删除 | **1400 → 0** | 1400 → 1400 完好 | **381 → 0** |

对照组那一行就是"假脱敏"的定义:黑框画上了、文字也删了,但框下的图片与矢量仍然留在文件里,几秒即可提取 —— 正是竞品评测反复警告的「AI 标记 ≠ 脱敏」。

**实施内容**

| 文件 | 改动 |
|---|---|
| `src/core/types.ts` | 新增 `RedactItem` overlay + `'redact'` tool |
| `src/core/writer/redact.ts` | `RedactEdit.mode`(`'text-only'` \| `'full'`);按 `(页, 模式)` 分组,每组独立注释 + 独立参数;导出 MuPDF 常量语义 |
| `src/features/export/exportPdf.ts` | 涂黑 overlay 以 `'full'` 提交;**零文本编辑时也会执行 redaction**(旧逻辑会整段跳过);失败即抛错 |
| `src/components/Toolbar.tsx` | R3 分组 + 涂黑工具 + 激活时的不可撤销警示 |
| `src/components/Inspector.tsx` | `RedactControls`:遮盖色 / 涂黑 / 涂白 / 备注 + 警示 |
| `src/features/viewer/CanvasInteractionLayer.tsx` | 拖拽创建涂黑框 |
| `src/features/overlays/ElementRenderer.tsx` | 实心遮盖块 + 编辑器内虚线描边(便于找到) |
| `src/hooks/useKeyboardShortcuts.ts` | `R` 绑定 |

**验证链(四层,逐层排除假象)**

1. **引擎(合成素材,像素隔离)** — `experiment-redact.mjs`:含对照组,证明参数确实是差异来源。
2. **引擎(真实 fixture,不画黑框)** — 排除"黑框盖住未删除内容"的假象:区域变成纯白纸(mean 255.0,std 52.2→0.0),底层扫描数据确实被抹除。
3. **应用端到端(真实 fixture,真实 UI 拖拽 → 导出)** — `verify-redacted-export.mjs`:被覆盖区域变为纯黑(std→0.0),区域外统计量逐位相同(57.5→57.5),未误删。
4. **自动化回归** — `tests/integration/redact-export.spec.ts`(6 例)+ `tests/unit/redact-modes.spec.ts`(11 例)。均已确认在改动前的代码上会失败。

**已知代价**

`image_method = PIXELS` 会重新编码被覆盖的图片,扫描件导出体积显著增大。实测 fixture S5:

| 模式 | 导出体积 | 是否正确脱敏 |
|---|---|---|
| 原文件 | 170.6 KB | — |
| `NONE` (0) | 171.3 KB | ❌ 完全不脱敏 |
| `PIXELS` (2) | 4275.7 KB | ✅ 局部正确脱敏 |
| `REMOVE` (1) | 171.2 KB | ⚠️ 会把整张图片删掉(框外内容一并丢失) |

**可行优化**:当涂黑框完整覆盖某张图片时,对该图改用 `REMOVE`,体积可回到 KB 级。需要先做图片 bbox 内省。

**安全约束(不可回退)**:涂黑 overlay 存在时,redaction 失败必须抛错中止导出,不允许走白底兜底降级。宁可导出失败,也不能交付一份"看起来已脱敏、实际仍可提取原文"的文件。

## 6. 需要注意的反面教训

1. **不要做「假脱敏」**。评测明确指出:黑矩形覆盖不是脱敏,原文仍可提取。你已有真 redact,别在 UI 上退化成画黑框。
2. **AI 功能的三个已知坑**(来自评测):数字幻觉、复杂多栏布局读错顺序、表格推理不可靠。若将来做 AI,**不要**用 AI 结果直接改写文档内容。
3. **转换保真度是陷阱**。导出 Word/Excel 的布局错乱是评测反复批评的点。你的项目专注 PDF 原生编辑是**明智的取舍**,不要轻易扩张到这个领域。
4. **功能密度 ≠ 好用**。PDF Expert 的评测结论是「工具很多但不觉得被淹没」,靠的是分组而非堆砌。你的 9 图标平铺正是反例。
